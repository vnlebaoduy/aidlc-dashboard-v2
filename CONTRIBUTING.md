# Contributing to AI-DLC Dashboard v2

Thanks for taking the time to look at this project. Bug reports, translations,
documentation fixes and code changes are all welcome. This guide explains how the
project is built, what a good change looks like, and how to get it merged.

## Code of Conduct

Everyone who takes part agrees to the [Code of Conduct](CODE_OF_CONDUCT.md). Report
unacceptable behaviour to the maintainer through GitHub
([@vnlebaoduy](https://github.com/vnlebaoduy)); reports are handled privately.

## Scope

This repository is the dashboard for **AI-DLC v2** runs. It reads the v2 record
layout (`aidlc/spaces/<space>/intents/<record>/`); v1 support lives in
[wowzoo/aidlc-dashboard](https://github.com/wowzoo/aidlc-dashboard). A change that
alters scan or model semantics must say why and include fixtures that prove the new
shape is real.

Two constraints are not negotiable:

1. **The workspace is read-only.** No route or client code may write to a workspace.
   The only writes are `data/usage.db` and `data/recent-workspaces.json`, outside any
   workspace.
2. **The security model stays.** Loopback bind, the `Host` guard on every route, the
   cross-site guard on `/select`, `/open` and `/api/refresh`, and the file jail for
   artifact reads and OS-editor launches.

## Ways to contribute

- **Bugs.** Open an issue with the template. Include what you expected, what happened,
  the browser and OS, and — if the numbers are wrong — the shape of the record that
  produced them (with anything private removed).
- **Features.** Open an issue first so the design can be agreed before code. Explain
  the question the page or panel answers; this dashboard is organised by question.
- **Translations.** English and Vietnamese are first-class. See
  [Translations](#translations).
- **Documentation.** Fixes to `README.md`, `DESIGN.md` and this guide are welcome.
- **Reviews.** Reproducing a bug, testing a pull request, or checking screenshots at
  the three widths is genuinely useful.

## Development setup

Requirements: [Bun](https://bun.sh) 1.4+.

```bash
git clone https://github.com/vnlebaoduy/aidlc-dashboard-v2.git
cd aidlc-dashboard-v2
bun install
(cd web && bun install)
bun run dev -- --root fixtures/reference
```

Open <http://127.0.0.1:5173>. Vite serves the UI with HMR; the Bun API runs on `:4329`
with `--watch` and is reached through Vite's proxy. Port 4329 keeps dev clear of a
dashboard already running on 4321.

`fixtures/reference` is a small synthetic AI-DLC v2 run. Use it instead of a real
workspace in issues and tests; it has no private content and covers every page. If
you need a real tree to reproduce something, describe its shape rather than
attaching the tree.

Useful commands:

| Command | Does |
|---|---|
| `bun run dev` | API (watch) + Vite (HMR) |
| `bun run build` | typecheck web + production build into `web/dist` |
| `bun run typecheck` | server and web `tsc` |
| `bun run lint` / `bun run format` | Biome |
| `bun test` | all server tests |
| `bun run verify` | typecheck, lint, tests and build — the merge gate |

There is no separate test runner for the client; browser-level checks are done by
hand against the dev server (see [Verification](#verification)).

## Project layout

```
server/          Bun server: HTTP, scan, model assembly, credit
  scan/           audit, state, questions, outcomes, discovery, file jail
  model/          types, status derivation, freshness
  credit/         Kiro credit store, Claude Code transcript reader
  test/           bun:test suites
web/src/
  routes/         TanStack file routes
  components/     shared building blocks (page, status, charts, picker, UI kit)
  features/       page-specific code, one folder per page
  i18n/           typed catalogues (catalog.ts, en.ts, vi.ts, chrome.ts)
  lib/            API client, theme, formatting, notifications
fixtures/reference/  synthetic run used by dev and tests
```

Rules that follow from this layout:

- `server/` is Bun code and must stay free of DOM types.
- The client imports server **types**, plus pure helpers
  (`server/model/status.ts`, `server/i18n/common.ts`, `server/i18n/locale.ts`)
  through the `@server/*` alias. Never value-import a server module that touches
  `node:*`.
- Wire types belong in `server/api-types.ts`; model types in `server/model/types.ts`.
- `web/src/routeTree.gen.ts` is generated by the TanStack Router plugin and is
  committed so a fresh clone typechecks. Do not hand-edit it.

## Design rules

Read [`DESIGN.md`](DESIGN.md) before any UI change; it owns the tokens, components,
page map, motion and notification rules. The short version:

- Status is always an **icon plus a word**, never colour alone.
- Icons are **lucide only**; no emoji or unicode glyphs as icons.
- One yellow emphasis per view; yellow is a fill, never text on white.
- Every chart needs `role="img"`, an `aria-label` and a `<title>` per mark.
- The client never renders workspace text as markup. Use the `Rich` allowlist for
  copy with inline markup; never use `dangerouslySetInnerHTML`.
- Charts and wide tables keep a minimum width and scroll on narrow screens.

## Copy and translations

All UI copy lives in `web/src/i18n`:

- `catalog.ts` declares the typed shape; `en.ts` and `vi.ts` implement it.
  A missing key is a typecheck failure, so add every string to both files in the same
  change.
- `chrome.ts` holds navigation and page leads.
- Workspace text (headings, file names, feedback) is quoted verbatim and never
  translated.

Write English first, then Vietnamese with matching meaning and tone — short and
factual. Do not machine-translate a whole file unreviewed; if you are unsure about a
term, open the pull request with the strings you know and ask for help with the rest.
A missing number is `—`, never `0`, in both languages.

## Making a change

1. **Open or find an issue.** Small fixes (typos, docs, a one-line bug) can go
   straight to a pull request. Anything that changes behaviour, layout or copy
   deserves an issue first.
2. **Branch.** Use a short descriptive branch: `fix/picker-scroll`,
   `feat/usage-window`, `docs/contributing`.
3. **Keep the change scoped.** One concern per pull request. Do not mix a refactor
   with a behaviour change, and do not reformat untouched files.
4. **Update everything that depends on the change.** Call sites, typed copy, tests,
   `README.md` or `DESIGN.md` when behaviour or appearance changed.
5. **Run the gate.**
6. **Describe the verification.** State the commands you ran and what you saw.

### Commit messages

Conventional Commits, in the imperative mood:

```
feat(picker): remove a workspace from the found list
fix(picker): keep scroll position when opening a folder
docs: document the notification tiers
ci: verify every push and pull request
chore(deps): bump lucide-react
```

Types in use: `feat`, `fix`, `docs`, `refactor`, `test`, `ci`, `chore`, `perf`.
A commit that changes behaviour must say what a reader will observe, not which file
moved.

### Pull requests

Fill in the pull-request template. A reviewable pull request has:

- a description of the problem and the change, linked to the issue;
- the smallest diff that solves it, with no unrelated churn;
- the verification evidence described below;
- no secrets, credentials, machine-specific paths or personal workspace data.

The maintainer reviews for correctness, regression risk and the constraints above.
Review comments are about the change, not the person; disagreements are settled with
evidence.

## Verification

Every change must pass the repository gate:

```bash
bun run verify
```

That runs typecheck, Biome, the full `bun test` suite (scan, model, credit, HTTP,
notifications) and the production build. A pull request with a failing gate will not
be merged.

For UI changes, also verify the actual surface in a browser:

- run `bun run dev -- --root fixtures/reference`;
- check the page in **light and dark** at **1440, 768 and 375 px**;
- confirm there is no overflow, clipping or overlap, and that the console is clean;
- exercise the interaction you changed, including the keyboard path and the empty,
  loading and error states where relevant.

Per the project rules, a smoke run of the changed path is required. Tests alone do
not prove a UI change.

### Tests

- Server tests use `bun:test` under `server/test` and beside the module they cover.
- Test behaviour a consumer can observe: boundaries, invariants, transitions,
  precedence and errors. Avoid tests that restate the implementation or assert
  incidental defaults.
- Add fixtures under `server/credit/parser/fixtures` or `fixtures/reference` rather
  than committing a real workspace.
- Never weaken or delete a failing test to make a build green; fix the cause or
  explain why the expectation was wrong.

## Reporting a bug

Use the bug-report template and include:

- what you expected and what happened;
- steps to reproduce, from launching the server to the page and click;
- the dashboard version (`/api/meta`), Bun version, OS and browser;
- the shape of the record involved (stage, artifact kind) with private text removed;
- screenshots at the width where it appears.

Do not attach a real `aidlc/` tree, `usage.db`, or anything containing client work.

## Security

Do **not** open a public issue for a vulnerability. Follow [`SECURITY.md`](SECURITY.md)
and report it privately. The server intentionally has no authentication; exposing it
beyond a trusted network is a deployment choice, not a vulnerability. A bypass of the
`Host` guard, the cross-site guard, or the artifact jail is a vulnerability.
